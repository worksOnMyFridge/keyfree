# Keyfree: independent security review (2026-11-03)

The report as the reviewer (Claude Fable 5.1) wrote it, at commit `1754f45`, build v17. Its finding ids are renamed Y1..Y5, since F1..F20 are
taken in AUDIT.md. Its probe tests are not kept in the repository as written: the bad outcomes they show are now regression tests or limits, see
AUDIT.md.

Reviewer: an auditor session that had never seen the project. Scope: the clone at HEAD `1754f45`, with
attention to everything after `c553d87` (the last outside review): `packages/keyfree/src/near.ts`,
`core.ts`, the retry logic, `explorer/index.html`, `setup/policy.mjs`, and the contract as the place where
authority lives. Read-only toward every network; nothing was sent, signed or created. No key material was
read. Method: read all the code first and form a threat model, then read AUDIT.md / CLAIMS.md / SECURITY.md,
then try to break the strongest statements, proving each suspicion with a unit test in the clone where
possible. Probe tests are appended to `contract/src/tests.rs` as `mod fresh_audit` (lines 2226-2381) and run
offline on near-sdk's mocked chain with the real contract code.

Baseline before any change: `cargo test -- --test-threads=1` 168 passed; `npm test` in `packages/keyfree`
78 passed. With the eight probes added: 176 passed (`cargo_test_with_probes.log`).

Severity scale: High = funds or authority can be taken; Medium = the system's promises are broken or it
can be frozen in a way the docs do not state; Low = operational dead end or misleading statement; Info = note.

## Findings

### Y1 (Medium, proved) - A Read-MPC-confirmed journal line can be reverted to "signed", or turned into a stuck, policy-freezing nonce, by an ordinary re-sign

**Who:** the agent (the agent key, a prompt-injected agent, or a stolen agent key), or the owner; also two
honest operators by accident (one running `confirm` on a schedule, the other `retry`). No council key needed.

**Where:** `contract/src/lib.rs`
- `confirm` (913-922) requires the line to be `SIGNED` at call time and starts an async Read MPC call;
  `on_confirmed` (988-995) sets `CONFIRMED` without checking anything else.
- `resign` (829-846) / `resign_proxy_upgrade` (812-824) only require `SIGNED` and `pending.is_none()`; they
  do not know a confirmation is in flight.
- `handle_signed` (887-908) on success calls `set_line(.., SIGNED)` (1130-1140) unconditionally; on failure
  calls `park` (871-879), which treats any line that is not `SIGNED` as a new request and sets `self.stuck`.

**What happens:** the agent calls `confirm` for nonce N (tx A landed), then immediately `resign` for the
same N. Read MPC answers first: the line becomes `CONFIRMED` (a verified fact). Then the MPC answer for the
re-sign arrives:
- if it is a signature (P1): the line goes back to `SIGNED` with the hash of tx B, a transaction that can
  never land (nonce N is spent by A). Because `confirm` binds the line's own tx hash, that line can never be
  confirmed again. The README's "the journal records what happened on chain, not what was intended" and
  CLAIMS 5 no longer hold for that line; the explorer shows the lie as a warning pill.
- if the MPC fails, or the re-sign is `release`d after the timeout (P1b): `park` finds the line is not
  `SIGNED` (it is `CONFIRMED`) and sets `stuck = N`. From then on every `request_deploy` /
  `request_proxy_upgrade` on every chain is refused ("an earlier request did not finish", lines 771, 803).
  The tool's `retry` sees the nonce already used on chain and stops, pointing at `confirm_stuck`
  (`core.ts:363`), which neither the CLI nor the MCP server exposes (`cli.ts`, `mcp.ts`: no such command).
  A raw `retry` call unfreezes the policy but leaves the line permanently downgraded as in P1. A hand-built
  `confirm_stuck` with tx A's signature and gas fields is the only clean way out.

**Proof:** `tests::fresh_audit::p1_resign_in_flight_turns_a_confirmed_line_back_into_signed` and
`p1b_a_failed_resign_after_confirmation_makes_a_landed_nonce_stuck` (both pass, i.e. the bad outcome
happens). P1b asserts `get_open()["stuck"] == 2` after `handle_signed(Err)`, and again after `release()`.

**Suggested fix:** in `handle_signed` and `park`, read the line's status first: if it is `CONFIRMED`,
log and drop the answer (never overwrite, never park). Additionally refuse `resign`/`resign_proxy_upgrade`
while a `confirm` for that key is in flight (a small `confirming: Option<String>` set in `confirm`, cleared
in `on_confirmed`). Keep the two probes as regression tests.

### Y2 (Medium, proved) - One stuck request plus any single brake freezes the whole policy, and only a widening through the delay can undo it

**Who:** any MPC failure (timeout, bad answer) followed by any one council member braking the request's
chain, code, factory or gas cap: an honest member reacting to an incident, or a thief with one council key
who waits for an MPC hiccup. The agent cannot cause it alone.

**Where:** `contract/src/lib.rs`
- `stuck: Option<Pending>` (237) is one slot for all chains; `request_deploy` (771) and
  `request_proxy_upgrade` (803) refuse while it is set.
- `retry` (848-858) is the only path that clears it by signing, and since the third review's X4 fix it
  obeys the brakes through `require_not_braked` (1163-1172).
- `handle_stuck_confirmed` (953-966) is the other way out and needs the transaction to have landed in a
  Finalized block.
- No council method touches `stuck`: not `pause`/`unpause`, `revoke_agent`, `remove_code`,
  `disable_chain`, `remove_factory`, `lower_limits`, `lower_budget`, nor any `cancel_*`.

**What happens:** nonce N on chain A is stuck. The guardian removes its code (or disables chain A, removes
its factory, or lowers the gas cap below its gas). `retry` is now refused forever; `confirm_stuck` has no
landed transaction to prove. Every chain is blocked. The council's only exit is to re-allow exactly what it
braked (`AllowCode` / `EnableChain` / `SetFactory` / `SetLimits`, each a rule proposal through
`rules_delay_sec`) and then let the agent sign the request it wanted to stop. A retirement is still
possible (`apply_role(Retire)` checks `pending`, not `stuck`), but that is the end of the policy. This
interaction was created by the X4 fix and is not listed in AUDIT.md or SECURITY.md; SECURITY.md says a
stolen council key can do "nothing more" than brake, which is true, but a brake on a stuck request is a
policy-wide, delay-gated freeze, not a brake on one request.

**Proof:** `p2a_a_braked_stuck_request_cannot_be_retried` (a real `request_deploy`, MPC failure,
`remove_code`, then `retry` by the owner panics "code not on the allow list"),
`p2b_a_stuck_request_on_one_chain_blocks_requests_on_every_other_chain` (stuck on 84532, `disable_chain`,
a healthy chain 421614 refuses "an earlier request did not finish"),
`p2c_no_brake_or_council_call_clears_the_stuck_slot` (every brake and a 2-of-3 unpause leave `stuck == 4`).

**Suggested fix:** two parts. (1) Make `stuck` per chain (`IterableMap<u64, Pending>`), so a stuck request
on one chain never blocks another. (2) Give the council a brake that can end a stuck or unwanted nonce:
`cancel_nonce(chain, nonce, fees)`, which has the MPC sign a 0-value, empty-data transaction to the
policy's own address at that nonce (21 000 gas), recorded as a journal kind "cancelled". That is the only
way an issued EIP-1559 signature can be made worthless, and it also addresses Y3. Until then, document that
a brake must not be applied to a stuck request's chain/code/factory unless the council accepts a full freeze.

### Y3 (Medium, proved; partly known) - No brake can recall or invalidate a signature once issued; `remove_proxy_upgrade` is moot after the request; a withheld signature holds every later nonce hostage

**Who:** the agent, or whoever holds a signed raw transaction (they are public on NEAR, as SECURITY.md says).

**Where:** `contract/src/lib.rs`: the allowance is consumed in `request_proxy_upgrade` (806) before the MPC
answers; `remove_proxy_upgrade` (719-724) removes an allowance that is already gone; `resign_proxy_upgrade`
(812-824) checks only `SIGNED`, the gas cap, fees and `require_not_braked`, which for a proxy line checks
only the chain and the gas cap (1166-1171). There is no method that puts other content on a nonce, by design
(N8), so nothing can race a held-back signature.

**What happens:** EIP-1559 transactions do not expire. The council allows `upgradeTo(V2)` on the treasury
proxy; the agent requests it and gets the signature but does not broadcast. The council later finds V2 is
bad: `remove_proxy_upgrade` does nothing (the allowance was used); `pause`, `disable_chain` and
`revoke_agent` stop new signatures only. The holder lands `upgradeTo(V2)` whenever it suits them, and because
nonces are sequential, nothing the council signs at nonce N+1 (an `upgradeTo(V3)`) can land before it. The
same holds for a deploy of code that was later removed. SECURITY.md ("A signed transaction is public ... it
can only spend the nonce on the content the rules allowed") and X5 acknowledge that a signature can still
land; what is not stated is that the brake table ("remove code or an allowed proxy upgrade", SECURITY.md
lines 15-17) does not apply to anything already requested, and that a withheld nonce blocks the council's
own corrective transactions.

**Proof:** `p3_remove_proxy_upgrade_cannot_stop_an_upgrade_that_was_already_requested`: after the request is
signed, `remove_proxy_upgrade` leaves `allowed_upgrades` empty and `resign_proxy_upgrade` still produces
the same `upgradeTo(v2)` calldata at the same nonce. The existing test
`a_deploy_never_takes_the_nonce_of_a_proxy_upgrade` shows no other content can take the nonce.

**Suggested fix:** the `cancel_nonce` brake from Y2 (a self-transfer of 0 at that nonce with a fee above the
held signature's). State plainly in SECURITY.md that brakes stop future signatures only, and that
`remove_proxy_upgrade` is useful only before the agent's request.

### Y4 (Low) - A chain whose nonce is ahead of the policy's cannot be repaired without a contract upgrade

**Who:** the council, after opening a chain with the wrong `next_nonce` (the setup script reads the real
count; a hand-made `AllowChain` may not), or any case where the address's nonce moves without the policy
knowing.

**Where:** `validate_rule` for `AllowChain` (1083-1086) refuses a second `AllowChain`; `disable_chain` keeps
the nonce (708-713); only `handle_signed` and `handle_stuck_confirmed` move it, never by hand (R18, by
design). The tool detects the state and says "tell the policy's council" (`core.ts:116`), but the council
has no method to act on it.

**What happens:** every signature for that chain is rejected by nodes forever; the chain is dead for this
policy. Not exploitable; an operational dead end that the docs present as "tell the council" without saying
the council can only upgrade the contract. Suggested: a council rule `ResyncNonce { chain, nonce }`, allowed
only upward and only when no journal line exists at or above the new nonce, through the rules delay.

### Y5 (Info) - Provenance shown by the explorer and checked by `setup` is self-reported or repo-reported

- `explorer/index.html` 273-275 labels `contract_source_metadata.link` "Source commit". That view is
  whatever the wasm says about itself; a laptop build can claim any commit. The page shows the code hash next
  to it but does not compare it with the hash the README pins, so a reader cannot tell from the page alone
  whether the running code is the reproducible build. Suggest: pin the expected base58 hash in the page and
  show "matches the reproducible build of commit X" / "does not match".
- `setup/policy.mjs` 74-82 "checks the wasm against the reproducible build": it checks the sha256 of the
  bytes fetched from `policy13` against `wasm_sha256` in `setup/config.example.json`, a number copied from the
  README. That is a consistency check between the live policy and the repo, not a rebuild. The README's
  wording ("installs it only if its sha256 equals the reproducible build") should say so.

I verified read-only that the live policy is consistent with the docs: `policy13.keyfree-lab.testnet` has 0
access keys; code hash `59xDZHtsvZH9iphdXbBvPcXkwvauwBRMCkuTfBUhLsHc` equals base58 of the README's sha256
`3db9d3e2...cba3` (checked offline); build `v17`, version 7; `contract_source_metadata` names commit
`ff925fd...` and the pinned image; `agent14` holds exactly one function-call key for the eight request
methods on `policy13` with no allowance; Base next nonce 14 = the address's on-chain nonce 14; Ethereum 3 = 3;
the treasury proxy's ERC-1967 admin slot is the policy's address and its implementation is V2; the Base
factory's `keyfree()` returns the policy's address; no request is pending or stuck; chain 421614 is open
with no budget (signs nothing, as v17 promises). I could not run the Docker rebuild (no Docker here), so
"the bytes are the reproducible build of that commit" rests on the authors' `build` workflow.

## Claims I tried to break and could not

- **"It never signs a hash someone hands it" / "builds the transaction itself."** True: every signing path
  goes through `tx_of` + `build_for_signing`; `confirm_stuck` only verifies a signature, it does not sign;
  the payload is always `keccak(0x02 || rlp)`.
- **"Vault(another owner) is other code."** True: the allow list holds the keccak of the full init code; the
  tool computes it from the artifact with `encodeDeployData`, and the contract hashes the bytes it is given.
- **"The agent key can only call the request methods."** Verified live; and `core.ts` `agent()` refuses to
  sign with any key that is not a function-call key limited to those methods on this policy (X3).
- **"A stolen council key can brake and nothing more."** True as to widening: one key cannot change roles,
  cannot unpause, cannot shorten a delay, cannot apply an unready proposal (existing tests and property tests
  cover it; I re-read every path). But see Y2 for what a brake can do to a stuck request.
- **One content per nonce, nonce never down.** Held in every path I traced, including `confirm_stuck` with
  caller-supplied gas fields (the signature must still recover to the policy's address over the rebuilt
  content) and `handle_stuck_confirmed` with a concurrent `retry` (the `still` check). The P1/P1b problem is
  not two contents on a nonce; it is the journal and the `stuck` slot disagreeing with the chain.
- **Daily budget.** `spent_after` is checked and written on every signing path (request, resign, retry,
  proxy variants; previews refuse too); `confirm_stuck` does not touch it (probe P4); the overflow is
  saturating; a chain with no budget signs nothing.
- **Callbacks never panic.** `callback_json` reads raw bytes with a size cap; `handle_signed`,
  `on_confirmed`, `on_stuck_confirmed`, `on_derived` have no panicking path I could find.
- **Migration.** Each older layout is a strict prefix of the next; borsh refuses trailing bytes, so the
  three `try_from_slice` attempts cannot misparse one layout as another.
- **Retirement.** 2 of 3, beneficiary must be a council member who approved, account never deleted (X1).
- **Tool, after c553d87.** `near.ts`: the transaction is signed locally and its hash computed before
  sending, so a lost answer is looked up, not re-signed; a new nonce is used only after an `InvalidNonce`
  and a 3 s lookup that finds nothing (a lagging fallback node could in theory defeat that window, but the
  contract then refuses the duplicate: `pending` set, or the salt already used, or the allowance consumed;
  not proved, low value). `guardFetch` only wraps the configured NEAR URL, so viem's EVM calls are untouched;
  a `send_tx` resent to a fallback node is the same hash. `checkSigned` verifies chain, nonce, to, data,
  value 0, type and the recovering address before broadcast; `sameAsLine` compares a retry with the journal
  line. `retryUnlanded` picks only the chain's first unlanded nonce, so through the tool the Y1 race needs a
  lagging EVM node or a raw contract call (which CLAIMS 9.3 treats as in scope). Error text from nodes is
  stripped of control and bidi characters and URLs are reduced to hosts; what a lying NEAR node can still do
  is put words into a "refusal" the model reads, which SECURITY.md already states.
- **Explorer page.** Every value from a node passes through `esc` or a regex before it reaches `innerHTML`;
  links are built only from `https://` strings or validated hex; `view` errors are split into "refused"
  (contract words) and "no answer"; the page states what it could not read instead of guessing; the CSP
  allows only inline script/style and https connections. I found no injection or false-fact path. I did not
  run it in a browser (static review only).
- **Factory.** `deploy` is `msg.sender == keyfree` only; `Deployed` is emitted only on success; the policy's
  `expected_address` equals CREATE2 with the factory as deployer, and the tool checks it against viem.
- **Secrets in the repo.** No `ed25519:` secret keys or `private_key` values in the tree; key files are
  gitignored; the docs' example key is a placeholder.
- **A stranger.** Can call `confirm` (by design; the policy pays 1 yoctoNEAR per call and the MPC does the
  work, probe P5) and `setup` before the address is derived; cannot request, release, brake or propose.

The nearcore sandbox (needs Linux/Docker), the CI workflows and `attacks/run.mjs` internals, the factory

nothing was sent anywhere.

## Overall judgement

The authority model is sound and I could not get past it: no key, one content per nonce, an allow list over
the whole init code, delays that nothing shortens, brakes that one member can pull. The claims in the docs
match the live state I could read. What is wrong is in the seams between asynchronous steps: the journal and
the single global `stuck` slot can disagree with the chain after an ordinary `confirm`/`resign` overlap (Y1),
and the fix from the last review (brakes on retry) turned a stuck request into a policy-wide freeze that only
re-widening can clear (Y2). Both are fixable in a few lines and should be fixed and regression-tested before
anyone relies on the journal as "what happened on chain". The deeper design gap (Y3) is that nothing can
cancel a signature once issued: a council `cancel_nonce` brake would close Y2 and Y3 together and make the
brake table literally true. I would trust this on testnet as a demonstration; for value on mainnet I would
want Y1-Y3 closed and a human audit of the MPC payload encoding.
